# 团队复用指南 —— 其他人拉取本仓库后如何使用

> 适用对象：拿到 `git@github.com:panweippc/ggzujian.git` 仓库的同事。
> 目标：clone 下来 → 复制示例 → 改几处配置 → 新项目的登录/认证/系统管理/操作日志/账号区就能用。
> 阅读时间：约 10 分钟；实际接入一个项目：约 2～3.5 小时。

---

## 一、先搞清楚：发包 vs 不发包，区别是什么？

这两种方式**只是"别人怎么拿到这两个包"不同，包的代码完全一样**。业务代码不用改，切换时只改一行依赖声明。

| 维度 | 不发包（本仓库当前模式） | 发包（GitHub Packages / npm） |
|---|---|---|
| 别人怎么拿到 | `git clone` 本仓库，用 `file:` 指向本地路径 | `npm install @panweippc/auth-kit` 从 registry 拉取 |
| 认证要求 | 只需 **git 仓库权限**（你的 SSH key） | 需 **npm token/PAT**，每人配 `.npmrc` |
| 拿到什么 | 完整仓库：源码 + 示例 + 文档，可看可改可调试 | 只发 `package.json` 里 `files` 白名单的文件（源码 + README） |
| 版本管理 | git commit + tag（本仓库用 `v1.0.0` 这类标签） | npm 语义化版本 + `package-lock.json` 锁定 |
| 更新方式 | `git pull` 即更新，源码改动即时生效 | 维护者 `npm publish` → 使用者 `npm update` |
| 回滚方式 | `git checkout v1.0.0` 或指定 commit | `npm i @panweippc/auth-kit@1.0.0` |
| 离线可用 | clone 后可完全离线开发 | 需联网访问 registry |
| 适合场景 | 小团队、共用仓库、内网、想直接看/改源码 | 多团队、跨仓库、要求稳定版本契约、不想暴露源码 |
| 主要代价 | 每个人 clone 的位置不同，`file:` 相对路径要按自己目录改一次 | 需维护 token、发包流程；包更新要重新发版 |

**本仓库的结论：现在就用"不发包"模式。** 仓库本身就是分发的载体，团队 clone 后用 `file:` 引用即可，零 token、零发包流程、改源码即时可见。

> 什么时候该发包？当出现"不相关团队要引用、但不想给他们仓库权限"或"需要稳定版本契约/锁定依赖"时再发。届时按本文第五节切换，**业务代码一行不用改**。

## 二、拉取后复用的完整步骤

### 第 1 步：clone 仓库

```bash
git clone git@github.com:panweippc/ggzujian.git
cd ggzujian
```

前提：本机已配置 GitHub SSH key（与推送 wygl/qygl 用的是同一把）。没配置过的话先生成 key 并添加到 GitHub 账号。

确认拿到内容：

```bash
ls
# README.md  docs/  examples/  package.json  packages/
```

其中你真正会用到的是：
- `packages/auth-kit` —— 后端包
- `packages/admin-ui` —— 前端包
- `examples/starter` —— 可直接复制运行的最小项目骨架
- `docs/新项目接入指南.md` —— 逐行接线说明（`docs/团队复用指南.md` 就是本文）

### 第 2 步：复制 starter 到你的项目

建议把 `examples/starter` 整个复制出来，作为新项目的起点：

```bash
# 假设你打算把新项目放在 D:\work\myapp，与 ggzujian 同级
cp -r examples/starter D:/work/myapp
```

复制后结构：

```
D:/work/
├── ggzujian/            ← 刚 clone 的公共组件仓库
│   └── packages/
│       ├── auth-kit/
│       └── admin-ui/
└── myapp/               ← 你的新项目
    ├── server/          ← 从 starter 复制
    └── web/             ← 从 starter 复制
```

### 第 3 步：改 `file:` 路径（**最容易踩的坑**）

starter 里的路径是相对它自己在仓库内的位置写的（`../../../packages/...`）。复制到你的项目后，**必须按你自己的目录结构调整**。

以上面"myapp 与 ggzujian 同级"为例：

`myapp/server/package.json`：

```json
{
  "dependencies": {
    "@panweippc/auth-kit": "file:../ggzujian/packages/auth-kit",
    "express": "^4.19.0",
    "cors": "^2.8.5",
    "mysql2": "^3.9.0"
  }
}
```

`myapp/web/package.json`：

```json
{
  "dependencies": {
    "vue": "^3.3.0",
    "vue-router": "^4.2.0",
    "pinia": "^2.1.0",
    "element-plus": "^2.2.0",
    "@element-plus/icons-vue": "^2.1.0",
    "axios": "^1.6.0",
    "@panweippc/admin-ui": "file:../ggzujian/packages/admin-ui"
  },
  "devDependencies": {
    "vite": "^5.0.0",
    "@vitejs/plugin-vue": "^5.0.0",
    "typescript": "^5.3.0"
  }
}
```

同时改 `myapp/web/vite.config.ts` 的 fs 白名单（否则 Vite 会拒绝访问仓库外的包源码）：

```ts
server: {
  port: 3008,
  proxy: { '/api': 'http://127.0.0.1:3010' },
  fs: { allow: ['..', '../ggzujian/packages/admin-ui'] }
},
optimizeDeps: { exclude: ['@panweippc/admin-ui'] }
```

> 路径规则：`file:` 后面是**相对当前 package.json 所在目录**的路径。用正斜杠 `/`，Windows 下也别用反斜杠。
> 如果你把 ggzujian 放在别处（比如 `D:/libs/ggzujian`），改成对应的相对路径，或用绝对路径 `file:D:/libs/ggzujian/packages/auth-kit`。

### 第 4 步：装依赖

```bash
# 后端
cd myapp/server && npm install

# 前端
cd myapp/web && npm install
```

后端包依赖（bcryptjs / jsonwebtoken / dotenv）会随 `file:` 安装自动装好；前端包把 Vue / Element Plus / axios / pinia 声明为 peer，需项目自己装（starter 的 package.json 已列全）。

### 第 5 步：改你自己的配置（只改这几处）

| 想改什么 | 改哪里 |
|---|---|
| 系统名称、Logo、登录页文案、按钮文字 | `web/src/config.ts` |
| 数据库地址、JWT 密钥、管理员初始密码 | `server/.env`（从 `.env.example` 复制） |
| 用户表结构、查用户的 SQL | `server/server.js` 里的 `findUserByUsername` + `server/db.sql` |
| 用户管理/操作日志的字段与接口 | `web/src/api.ts` 和各视图的 `config` 对象 |
| 业务页面 | `web/src/views/HomeView.vue` 开始写 |

**密钥/密码只写 `.env`**，代码里一律占位符或引用变量（这是团队约定）。

### 第 6 步：跑起来并验证

```bash
# 1. 建库
mysql -u root -p < server/db.sql

# 2. 起后端（:3010）
cd server && npm run dev

# 3. 起前端（:3008）
cd web && npm run dev
```

打开 `http://localhost:3008`，用 `db.sql` 里的初始管理员登录。验证清单：

- [ ] 登录页能显示你的品牌名，验证码可刷新、可登录
- [ ] 登录后账号区头像下拉能展开，退出登录可用
- [ ] 系统管理能列出用户、可新增/编辑
- [ ] 操作日志能列出登录等操作记录（不是空表、不是列错位）
- [ ] 改密码后旧 token 失效（指纹校验生效）

逐项配置细节和完整代码见 **[新项目接入指南.md](新项目接入指南.md)**。

## 三、日常更新与版本

公共组件仓库会继续修 bug、加功能。你这边更新：

```bash
# 在 ggzujian 目录
git pull

# 你的项目里重新安装，让 file: 依赖指向最新源码
cd myapp/server && npm install
cd myapp/web && npm install
```

版本以 git tag 为准：

```bash
git tag           # 看有哪些版本
git checkout v1.0.0   # 需要稳定版本时切到标签，避免用到未验证的改动
```

> 建议：生产项目固定到某个 tag，测试项目跟 `main`。公共包升级前先看 CHANGELOG/提交信息。

## 四、常见问题

1. **`Cannot find module '@panweippc/auth-kit'`**
   `file:` 路径写错。检查相对路径是否从**当前 package.json 所在目录**算起，并用 `node -e "console.log(require('fs').existsSync('...'))"` 验证目录存在。

2. **Vite 报 `Failed to resolve import` 或拒绝访问 node_modules 外的文件**
   `vite.config.ts` 的 `server.fs.allow` 没包含 admin-ui 路径；按第 3 步补上。`optimizeDeps.exclude` 也要保留。

3. **登录页能开，但点登录报错**
   检查 `web/src/config.ts` 的 API 地址是否指向你的后端（默认代理 `/api` → `:3010`），以及后端 `server/.env` 的 `JWT_SECRET` 等是否已填。

4. **操作日志表中字段错位（时间跑到 userId 列）**
   这是早期版本的缺陷，已修复。执行 `git pull` 更新到 `v1.0.0` 及以上即可。

5. **别人没有仓库权限**
   `file:` 模式要求每个人都能 clone 本仓库。找仓库管理员开通 SSH key 权限；如果跨组织协作不便，再考虑第五节发包。

## 五、未来切换到"发包"模式（可选）

当团队决定发包时，只需两步，**业务代码一行不用改**：

1. 维护者在公共包仓库配置 `.npmrc` 并发布：

```bash
npm login --registry=https://npm.pkg.github.com
cd packages/auth-kit && npm publish
cd ../admin-ui && npm publish
```

2. 每个消费项目把依赖声明从路径改为包名：

```diff
- "@panweippc/auth-kit": "file:../ggzujian/packages/auth-kit"
+ "@panweippc/auth-kit": "^1.0.0"
```

并在项目根目录 `.npmrc` 加：

```
@panweippc:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${GITHUB_TOKEN}
```

然后 `npm install` 即可。前端组件的 props、后端工具的函数签名都不变。
